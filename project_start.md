# Команда /start — инициализация системы самосовершенствования

Ты — архитектор рабочего окружения Claude Code. Твоя задача: через короткое интервью развернуть (или аккуратно обновить) полную систему файлов, скиллов, хуков и агентов для продуктивной работы над проектом.

Работай СТРОГО по фазам. Не пропускай фазы и не начинай генерацию раньше времени.

---

## ФАЗА 0 — Определение режима

1. Проверь наличие в корне проекта: `CLAUDE.md`, директории `.claude/`, файлов `LESSONS.md`, `ACCEPTANCE.md`, `DECISIONS.md`.
2. Если НИЧЕГО из этого нет → режим **NEW** (новый проект).
3. Если хоть что-то есть → режим **UPGRADE** (существующий проект).
4. В режиме UPGRADE: прочитай все существующие файлы конфигурации и запомни их содержимое. Ты будешь ОБЯЗАН сохранить накопленные знания (уроки, решения, правила) — их потеря недопустима.
5. Сообщи пользователю одним предложением, какой режим определён и почему.

## ФАЗА 0.5 — Подключение базы знаний (knowledge repo)

База знаний — отдельный git-репозиторий, общий для всех проектов пользователя. В нём накапливаются обобщённые уроки и скиллы; каждый новый проект берёт оттуда подходящий опыт и дописывает свой.

1. Проверь файл `.claude/knowledge.json` в корне проекта. Если он есть — возьми из него `url` и `localPath` и переходи к шагу 4.
2. Если файла нет — спроси пользователя через AskUserQuestion: «Укажи ссылку на репозиторий базы знаний». Первый вариант (рекомендуемый): `https://github.com/okhmat-anton/claude-start`. Также предложи вариант «Без базы знаний» — тогда пропусти все шаги, связанные с knowledge repo, но всё остальное выполняй как обычно.
3. Сохрани выбор в `.claude/knowledge.json`:
   ```json
   {
     "url": "https://github.com/okhmat-anton/claude-start.git",
     "localPath": "~/.claude/knowledge-repo/claude-start"
   }
   ```
4. Актуализируй локальный клон: если директория `localPath` существует — `git pull`; если нет — `git clone <url> <localPath>`. Если сеть/доступ недоступны — предупреди пользователя одной строкой и продолжай без базы знаний (не блокируй /start).
5. Проверь структуру знаний в клоне. Если её нет (репозиторий подключён впервые) — создай, закоммить (`knowledge: init structure`) и запушь:
   ```
   knowledge/
     INDEX.md          # оглавление: одна строка на единицу знания (что это, для какого стека, откуда)
     lessons/          # обобщённые уроки, по файлу на тему: <тема>.md
     skills/           # переносимые скиллы: <имя-скилла>/SKILL.md
     stacks/           # заметки по стекам: <стек>.md (python, vue, postgres …)
   ```
6. Подключи глобальные хуки и скиллы базы знаний: `bash <localPath>/tools/install.sh` (идемпотентно; добавляет в
   `~/.claude/settings.json` хуки UserPromptSubmit / PreToolUse(Bash) / SessionStart / Stop и ставит скилл `knowledge-gc`).
   Эти хуки сами подмешивают подходящие уроки в контекст по триггерам — поэтому уроки в проект больше НЕ копируются.
7. Прочитай `knowledge/FORMAT.md` (формат единицы знания) и `knowledge/INDEX.md` — он понадобится в Фазах 4 и 4.8.

## ФАЗА 1 — Создание файла интервью

Создай в корне проекта файл `PROJECT_INTERVIEW.md` со следующей структурой. Каждый вопрос — заголовок, под ним строка `Ответ:` (пустая). Вопросы сформулируй так, чтобы на них можно было ответить 1–5 словами.

Вопросы, помеченные ниже как **СТАНДАРТ**, пользователю НЕ задаются: создавай их в интервью уже заполненными значением стандарта (источник — база знаний, `knowledge/skills/standard-stack/SKILL.md`) с пометкой `(стандарт — можно переопределить)`. Если пользователь правит такой ответ — его вариант всегда приоритетнее стандарта.

В режиме UPGRADE: предзаполни ответы всем, что смог достоверно извлечь из существующих файлов и кода проекта, и пометь такие ответы суффиксом `(автозаполнено — проверь)`. Пользователь исправит неверное.

### 27 вопросов

**О продукте**
1. Что это за продукт? (одна фраза)
2. Кто основной пользователь?
3. Стадия проекта? (прототип / MVP / продакшн)

**Технологии**
4. Основной язык программирования?
5. Фреймворк / основные библиотеки?
6. База данных?
7. Пакетный менеджер? (npm / pnpm / pip / poetry / cargo …)
8. Стиль API? (REST / GraphQL / gRPC / нет API)

**Команды (единый стандарт)**
9. Команда запуска проекта? → **СТАНДАРТ**: `make run` (docker compose up -d --build); dev: `make run-dev`
10. Команда запуска всех тестов? → **СТАНДАРТ**: `make test` (pytest)
11. Команда линтера / форматтера? → **СТАНДАРТ**: `make lint` / `make format` (ruff; + eslint/prettier при фронте)
12. Команда сборки? → **СТАНДАРТ**: `make build` (docker compose build)

**Правила кода**
13. Стиль именования? → **СТАНДАРТ**: Python — snake_case (PEP8), JS — camelCase, классы/Vue-компоненты — PascalCase, константы — UPPER_CASE
14. Что категорически ЗАПРЕЩЕНО делать в коде? (например: any в TS, сырые SQL-запросы)
15. Какие директории нельзя трогать никогда?
16. Обязательные проверки перед завершением любой задачи? (тесты / линт / сборка / типы)

**Git и процесс**
17. Формат коммитов? → **СТАНДАРТ**: Conventional Commits — `type(scope): описание` (feat/fix/refactor/docs)
18. Стратегия веток? → **СТАНДАРТ**: только main (trunk-based, без feature-веток)
19. Что входит в Definition of Done для задачи?

**Окружение**
20. Как хранятся секреты? (.env / vault / нет секретов)
21. Есть ли деплой, и как он делается? → **СТАНДАРТ**: на сервере `make update` = git pull --rebase --autostash + docker compose build + up -d; хост и особенности уточняются при первом релизе

**Приоритеты и агенты**
22. Что важнее при компромиссах: скорость разработки, производительность или надёжность? (расставь: 1, 2, 3)
23. Главные текущие боли / повторяющиеся проблемы в проекте?
24. Нужен ли отдельный агент-ревьюер кода с накоплением памяти? (да / нет)
25. Язык общения Claude с тобой? (русский / английский)

**Мониторинг**
26. Нужна ли система мониторинга с внешней ссылкой для другого проекта? (да / нет)
27. Какие бизнес-метрики проекта отдавать в мониторинг? (например: пользователи, платные подписки, заказы, выручка — у каждого проекта свой набор; если в. 26 = «нет» — поставь прочерк)

В конце файла добавь блок:

```
---
СТАТУС: НЕ ЗАПОЛНЕНО
(поменяй на «ГОТОВО», когда ответишь на все вопросы)
```

## ФАЗА 2 — Ожидание заполнения (блокирующая)

1. После создания файла НЕ ДЕЛАЙ НИЧЕГО дальше.
2. Задай пользователю вопрос через инструмент AskUserQuestion с вариантами:
   - **«Да, заполнил»** — переходи к Фазе 3.
   - **«Нет, ещё нет»** — вежливо ответь «Хорошо, жду. Напиши, когда заполнишь, или запусти /start снова» и ЗАВЕРШИ работу. Ничего не генерируй.

## ФАЗА 3 — Валидация ответов (строгая)

1. Перечитай `PROJECT_INTERVIEW.md` с диска (не из памяти — пользователь его менял).
2. Проверь КАЖДЫЙ из 27 вопросов. Ответ считается ОТСУТСТВУЮЩИМ, если:
   - строка `Ответ:` пустая;
   - ответ — заглушка вида «?», «...», «todo», «потом»;
   - остался непроверенный маркер `(автозаполнено — проверь)` без правки пользователем — такой ответ считается принятым, НО перечисли эти пункты пользователю для явного подтверждения.
   - пометка `(стандарт — можно переопределить)` пробелом НЕ считается: это стандарт из базы знаний, отдельного подтверждения не требует; правка пользователя поверх стандарта всегда приоритетнее.
3. Если СТАТУС в конце файла не «ГОТОВО» — считай файл незаполненным.
4. **Если есть хоть один отсутствующий ответ:**
   - выведи нумерованный список незаполненных вопросов;
   - НЕ генерируй никакие файлы, даже частично;
   - вернись к Фазе 2 (снова спроси «Да, заполнил / Нет») и повторяй цикл валидации, пока все 27 ответов не будут заполнены.
5. Только когда все 27 ответов есть — переходи к Фазе 4.

## ФАЗА 4 — Генерация системы

Сначала выведи пользователю короткий план: какие файлы будут созданы (режим NEW) или изменены/сохранены (режим UPGRADE). В режиме UPGRADE дождись подтверждения плана через AskUserQuestion («Применить план? Да / Нет»). Затем создай:

### 4.1. CLAUDE.md — только постоянные факты
Компактный (цель — до 60 строк). Включи ТОЛЬКО то, что нужно в каждой сессии:
- одно предложение о продукте (в. 1–3);
- стек и точные команды: запуск, тесты, линт, сборка (в. 4–12);
- жёсткие правила: запреты, неприкасаемые директории, стиль именования (в. 13–15);
- git-конвенции (в. 17–18);
- приоритеты компромиссов (в. 22);
- язык общения (в. 25);
- правило: «Каждый найденный баг → регрессионный тест»;
- правило: «После каждой значимой задачи запускай skill retro (три вопроса: что пошло не так; что вышло быстрее
  ожидаемого; где владелец поправил — `.claude/corrections.log`). Хук Stop напомнит, если правок много, а retro не было»;
- правило: «Уроки из общей базы приходят сами через хуки по триггерам. Применил подсказку — отметь:
  `python3 <localPath>/tools/knowledge.py hit <name> --project <проект>`»;
- правило: «Перед выполнением любого нетривиального промта — skill prompt-gate: спроси недостающее, предложи улучшенный промт, подвергни сомнению спорные решения»;
- правило: «После каждого блока правок — skill simplify-review (агент-упроститель с памятью ответов)»;
- правило: «Первая задача дня начинается со skill daily-sync — pull базы знаний и новые скиллы/стеки» (только если база знаний подключена);
- ссылки: «Процедуры — в .claude/skills/, уроки — в LESSONS.md, решения — в DECISIONS.md».

НЕ клади в CLAUDE.md процедуры, чеклисты и длинные инструкции — им место в skills.

### 4.2. Журналы
- `LESSONS.md` — с шапкой-инструкцией. Формат записи ЕДИН для всех проектов (по нему работает автоматика):
  ```
  ### <slug-латиницей>
  Дата: ГГГГ-ММ-ДД · Триггер: <когда вспомнить: слова, команда, ошибка, путь> · В базе: candidate|mature|нет
  Контекст: одна-две строки.
  Урок: действие в повелительном наклонении.
  ```
  Правило зрелости: зрелость считается **по проектам, а не по повторам внутри одного**. Каждый урок в момент записи
  уезжает кандидатом в базу знаний (`knowledge.py new`, см. 4.3); замечен во втором проекте — становится зрелым там.
  Локальный журнал — накопитель незрелого: урок, ставший постоянным правилом проекта, переносится в CLAUDE.md /
  `.claude/rules/` / skill и удаляется отсюда. Импортированные из базы уроки в этот файл НЕ копируются — их доставляют хуки.
- `DECISIONS.md` — журнал архитектурных решений (ADR-лайт): дата, решение, почему, отвергнутые альтернативы.
- `ACCEPTANCE.md` — чеклист готовности задачи, собранный из ответов на в. 16 и 19.
- `.claude/corrections.log` — создаётся хуком автоматически: поправки владельца в чате («нет, не так», «опять»,
  «верни как было»). Читается retro и очищается им.

### 4.3. Skills (.claude/skills/)
- `retro/SKILL.md` — ретроспектива после задачи. Три вопроса, не один:
  1. **Что пошло не так** — неверное предположение, переделка, грабли, поздняя проверка.
  2. **Что вышло быстрее ожидаемого и почему** — приём, который стоит повторять (успех тоже урок).
  3. **Где владелец меня поправил** — прочитай `.claude/corrections.log` и память code-reviewer (`.claude/agent-memory/`),
     каждая поправка — кандидат в урок; после разбора файл очисти.
  Затем: (а) какие подсказки базы знаний в этой сессии помогли → `knowledge.py hit <name> --project <проект>`;
  (б) «какой урок сработал бы, если бы я его знал?» — если он в базе есть, но не пришёл, почини его триггеры
  (это дефект доставки, а не знания); (в) новый урок → запись в LESSONS.md **и сразу** кандидат в базу:
  `python3 <localPath>/tools/knowledge.py new <slug> --description "…" --stack … --seen-in <проект> --keywords "…"`,
  затем заполни тело по `knowledge/FORMAT.md`; (г) урок, ставший постоянным правилом проекта → CLAUDE.md / rules /
  skill, из LESSONS.md удалить. Финальный шаг — skill `knowledge-sync` (4.9). Ничего не нашлось — одна строка и конец.
- `done-check/SKILL.md` — прогон чеклиста из ACCEPTANCE.md перед завершением задачи.
- Если в ответе на в. 21 есть деплой — `release/SKILL.md` с процедурой релиза.
- У каждого skill: точное, конкретное поле description (когда именно его вызывать), тело до 100 строк.

### 4.4. Hooks (.claude/settings.json)
Собери из ответов на в. 10–11 и 15:
- `PostToolUse` (matcher: Edit|Write) → команда форматтера/линтера (в. 11);
- `Stop` → команда тестов (в. 10), если тесты существуют;
- `PreToolUse` (matcher: Bash) → блокировка `rm -rf` и записи в запрещённые директории (в. 15), скрипт положи в `.claude/hooks/`.
Если какой-то команды нет («нет») — соответствующий хук не создавай.
Глобальные хуки базы знаний (подмешивание уроков, corrections.log, контроль CLAUDE.md, напоминание про retro) уже стоят
в `~/.claude/settings.json` после Фазы 0.5 — в проекте их НЕ дублируй.

### 4.5. Subagents (.claude/agents/)
- Если в. 24 = «да»: `code-reviewer.md` с полем `memory: project` и инструкцией накапливать в памяти паттерны, конвенции и повторяющиеся ошибки проекта; доступ только на чтение.
- `explorer.md` — read-only агент для исследования кодовой базы и внешней документации, чтобы не засорять основной контекст.

### 4.6. Эмуляция агентской системы GitHub Copilot (VS Code)

Разверни поведение, повторяющее логику Copilot Agent Mode, средствами Claude Code:

**а) `agent-mode/SKILL.md`** — главный рабочий цикл (аналог Agent Mode). Description: «Используй для любой значимой задачи разработки». Тело skill:
1. **План-чеклист.** Перед любыми правками построй и покажи пользователю нумерованный todo-список шагов с чекбоксами `[ ]`. Крупную задачу дели на шаги ≤ 15 минут каждый.
2. **Пошаговое исполнение.** Выполняй шаги по порядку, после каждого отмечай `[x]` и показывай обновлённый чеклист одной строкой («Шаг 3/7 готов»). Если по ходу план меняется — покажи обновлённый план ПЕРЕД продолжением.
3. **Цикл самопроверки** (ключевое поведение Copilot): после каждого блока правок запускай команды проверки из CLAUDE.md (тесты → линт → сборка). Если есть ошибки — сам читай вывод, чини и запускай снова. Максимум 5 итераций автопочинки; если не сошлось — остановись, покажи оставшиеся ошибки и спроси пользователя, как действовать.
4. **Финальный отчёт.** В конце — компактная сводка: список изменённых файлов (по одному предложению на файл), что проверено, что осталось.

**б) Режимы чата** (аналог Ask / Edit / Agent):
- `ask-mode/SKILL.md` — «режим вопроса»: ТОЛЬКО отвечать и объяснять, ни одного изменения файлов, ни одной команды с побочными эффектами. Description: «когда пользователь просто спрашивает или пишет /ask».
- `edit-mode/SKILL.md` — «режим точечной правки»: менять ТОЛЬКО файлы, явно названные пользователем; не запускать команды, кроме проверочных; без расширения объёма задачи. Description: «когда пользователь просит поправить конкретный файл/место или пишет /edit».
- Полный агентский режим — это skill agent-mode из пункта (а).

**в) Правила с привязкой к путям** (аналог `.instructions.md` с `applyTo`): создай `.claude/rules/` и разложи туда правила из ответов на в. 13–15 и 23, которые касаются конкретных директорий или типов файлов, с glob-паттернами в frontmatter (например, правила для `src/legacy/**` или `**/*.test.ts`). Общие правила без привязки к путям остаются в CLAUDE.md.

**г) В CLAUDE.md добавь правило:** «Любую значимую задачу разработки выполняй через skill agent-mode: план-чеклист → шаги → самопроверка → отчёт».

### 4.7. Правила режима UPGRADE (критично)
- НИЧЕГО не удаляй и не перезаписывай вслепую.
- Существующие LESSONS.md и DECISIONS.md: сохрани всё содержимое полностью, можно только добавить шапку-инструкцию, если её не было.

### 4.13. Skill prompt-gate — доработка промта перед исполнением

Создай `.claude/skills/prompt-gate/SKILL.md`. Description: «вызывается перед выполнением любого нетривиального промта пользователя (новая задача — а не короткое уточнение по текущей)». Тело:

1. **Чего не хватает.** Определи, какой информации недостаёт для качественного выполнения (контекст, критерии готовности, ограничения, крайние случаи, примеры). Задай через AskUserQuestion не более 4 самых важных вопросов; по остальному прими явные допущения и перечисли их пользователю.
2. **Улучшенный промт.** Переформулируй задачу в улучшенный промт (цель, контекст, критерии приёмки) и покажи: «Понял задачу так: … Верно?». Работай дальше по подтверждённой версии.
3. **Сомнение в решениях.** Если в промте зашито готовое техническое решение — оцени его критически, а не исполняй молча. 4. **Не превращай чат в анкету.** Тривиальные запросы (вопрос, мелкая правка, продолжение уже согласованной задачи) пропускай без этого протокола.
5. **Память ворот.** Перед вопросами прочитай `.claude/prompt-gate-memory.md`; то, на что владелец уже отвечал (формат
   ошибок, нужен ли деплой, что считать готовым), не спрашивай снова — применяй. Каждый новый ответ записывай строкой
   `дата | вопрос | ответ`. Каждое сомнение в решении записывай `дата | что предлагал вместо | решение владельца | исход`
   и заполняй «исход» в retro (агент был прав / владелец был прав / не ясно). Перевес в пользу владельца за последний
   месяц — спорь реже и короче; перевес в пользу агента — спорь настойчивее. Создай файл с шапкой-инструкцией (пустой журнал).

### 4.14. Система мониторинга с внешней ссылкой (только если в. 26 = «да»)

Цель: другой проект пользователя по ссылкам сам забирает данные мониторинга этого проекта и выводит их в своём дешборде. Мониторинг состоит из ДВУХ обязательных частей — технической и бизнесовой, создаются обе.

1. Сгенерируй **вечный токен** — криптостойкую случайную строку (например, `openssl rand -hex 32`). Токен один на обе части. Срока действия у токена нет; ротация — только по явной просьбе пользователя (после ротации обнови файл `monitoring` и напомни заменить ссылки в проекте-потребителе).
2. **Технический мониторинг (отказоустойчивость)** — read-only endpoint `GET <базовый URL проекта>/monitoring/system/<токен>`: стабильный JSON, обязательно содержащий:
   - статус: работает ли система, health-чеки сервисов;
   - uptime — сколько времени система работает без падений;
   - загруженность сервера: память, процессор, диски, сеть.
3. **Бизнес-мониторинг** — отдельный read-only endpoint `GET <базовый URL проекта>/monitoring/business/<токен>`: JSON с бизнес-метриками из ответа на вопрос 27 (количество пользователей, платных подписок и т.п. — набор у каждого проекта свой). Если ответ на в. 27 пуст или неконкретен — уточни у пользователя через AskUserQuestion, какие бизнес-показатели отдавать.
4. Оба формата должны быть стабильны и пригодны для машинного чтения внешним дешбордом. Если HTTP-сервера в проекте нет — предложи пользователю через AskUserQuestion минимальный вариант реализации (отдельный лёгкий сервис).
5. Обе готовые ссылки целиком (URL + токен) запиши в файл `monitoring` в корне проекта — это постоянное место их хранения: отсюда пользователь в любой момент копирует ссылки и передаёт их проекту-потребителю.
6. Токен — секрет проекта: ссылки и токен никогда не экспортируй в базу знаний (см. «Общие запреты»).

### 4.15. Уборка базы знаний (knowledge-gc)

Скилл глобальный, ставится `tools/install.sh` в `~/.claude/skills/knowledge-gc` — в проект не копируй. Раз в месяц
(напоминает daily-sync) он читает `python3 tools/knowledge.py gc`: кандидаты из двух проектов → зрелые; показанные
много раз и ни разу не применённые → переформулировать или архив; ни разу не показанные → мёртвые триггеры; пересечения
триггеров → слить; длинные → разрезать; клон → синхронизировать с origin. Подробности — в самом скилле.

### 4.16. Регрессионные тесты поведения системы

В базе знаний: `evals/cases.json` — на каждую единицу знания эталонный промт или команда, на которые она обязана
сработать. `python3 tools/evals.py` (бесплатно, офлайн) проверяет доставку; `--live` (платно, вручную) гоняет
`claude -p` и проверяет, что агент реально применяет правило. Правило: новая единица — новый кейс; сломался кейс —
чинятся триггеры, а не удаляется кейс.
