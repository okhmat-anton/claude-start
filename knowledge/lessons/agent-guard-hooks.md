# Защитные хуки агента: разбирать команду программой и проверять на настоящих командах

Стек: любой агентный CLI-харнесс, где хук перехватывает команды до выполнения
(Claude Code и подобные).

## Шаблоны оболочки для разбора команды не годятся

Хук «не давать удалять и не давать писать в защищённые пути» пишется в лоб через
`case`/шаблоны — и сразу ловит не то:

- шаблон вида `*"rm "*` совпадает с «confirm », «form », «perform » — обычное чтение
  начинает блокироваться;
- перенаправление вывода нельзя искать одним символом: `2>&1` есть почти в каждой
  второй команде и не является записью в файл;
- ключи команды удаления пишут слитно и раздельно (`-rf`, `-fr`, `-r -f`) — один
  шаблон все варианты не покроет.

Правило: разбирать команду **программой** с границами слов, а не шаблонами оболочки.
Для команды удаления — собрать все её короткие ключи и проверить, есть ли среди них
одновременно «рекурсивно» и «принудительно».

## Блокировать изменение, а не упоминание

Защищённый путь в команде сам по себе ничего не значит. Чтение оттуда должно
работать — иначе агент не сможет ни расследовать инцидент, ни показать состояние.

Блокировка срабатывает, только когда рядом с защищённым путём стоит **меняющее**
действие: удаление, перемещение, копирование, перенаправление в файл, правка на
месте, смена прав. Поиск по файлу, вывод содержимого, список файлов — пропускаем.

## Прогнать на настоящих командах до включения

Обязательный шаг, который легко пропустить. Собери реальные команды проекта и
прогони хук на каждой, ожидая заранее известный ответ:

| Команда | Ожидание |
|---|---|
| рекурсивное удаление | блок |
| запись в папку с данными пользователей | блок |
| копирование файлов на сервер **с ключом доступа в аргументах** | пропуск |
| поиск по слову внутри защищённой папки | пропуск |
| просмотр журналов с `2>&1` в конце | пропуск |

Третья и четвёртая строки — это те самые ложные срабатывания. Хук, который блокирует
ежедневную выкладку, снимут в первый же день, и защиты не останется вовсе.

## Хук завершения не должен зацикливаться

Хук, который не даёт закончить работу с поломанным кодом, обязан проверять признак
«этот же хук уже сработал» и в этом случае пропускать. Иначе неисправимая ошибка
даёт бесконечный круг.

И проверять он должен **только изменённые файлы** — полный обход репозитория на
каждом завершении превращается в постоянную задержку, из-за которой хук отключат.

## Хук-скрипт читает stdin ДО вложенного интерпретатора

Вход хука (JSON с командой) приходит на stdin скрипта. Если скрипт передаёт
программу вложенному интерпретатору тоже через stdin (heredoc вида
`python - <<'EOF'`), heredoc занимает stdin целиком — JSON до программы не
доходит, разбор молча падает в «нет данных», и хук пропускает всё, включая то,
что обязан блокировать. Защита выглядит включённой, но не работает.

Правило: первой строкой скрипта сохранить вход (`INPUT=$(cat)`) и передавать его
интерпретатору через переменную окружения или аргумент. Обнаруживается это только
тестовым прогоном на настоящих командах (см. выше) — ещё одна причина не
пропускать этот шаг.

## Сообщение блокировки объясняет, что делать вместо

«Заблокировано» без продолжения читается как поломка, и агент начинает искать обход.
В тексте отказа: что именно нарушено, почему это правило существует и каким способом
задача решается законно (через интерфейс, через API, инструментом репозитория).
