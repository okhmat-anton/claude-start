# Единая точка проверок покрывает все языки проекта

Зрелый урок (2 повторения в одном проекте, python backend + flutter клиент; применимо к любому мультиязычному репо).

- Проявление: `make lint`/`make test` гоняли только проверки backend (ruff/pytest); анализатор и тесты клиента приходилось помнить и запускать руками отдельной командой — при правках клиента их легко забыть, агент тоже пропускает.
- Урок: канонические цели проверок (`make lint`, `make test`) обязаны покрывать КАЖДЫЙ язык репозитория (ruff + flutter analyze, pytest + flutter test и т.п.). «Запускать вторую команду руками» — не процедура, а источник пропусков: как только во втором языке появился первый тест или линтер — сразу вносить его в общую цель.
- Следствие для клиентских UI-багов: первый widget-тест заводится вместе с первым пойманным UI-багом (регрессия), а не «когда-нибудь»; чтобы приватный виджет стал тестируемым, достаточно сделать его публичным.
- Дополнение (2026-08, повторно в другом проекте): команда-проверка обязана СУЩЕСТВОВАТЬ в зависимостях — package.json может содержать скрипт `lint`, ссылающийся на бинарь, которого нет ни в devDependencies, ни в lockfile (проверка невыполнима в свежем окружении и молча пропускается). Наткнулся на «команда из правил не запускается» → сначала проверь lockfile/devDependencies, а не чини окружение; инструмента нет = долг проекта (завести зависимость), до тех пор — документированная замена проверки (build + type-check по правленным файлам) с фиксацией замены в отчёте.
