# История жалоб заказчика — источник недостающих правил

Контекст: заказчик не говорит «системная проблема с X», он говорит «не работает кнопка», через неделю «шапка
другая», ещё через неделю «размер слетел». Повторение видно только на длинном окне, и именно оно показывает,
какого правила в проекте не хватает. Три темы из пяти уже были общими модулями проекта — заказчик нащупывал
правила, а не просил чинить мелочи.

Урок:
- Выгружай только реплики человека; реплики, присланные во время работы агента, лежат отдельным типом записи
  (у Claude Code — `attachment` с `queued_command`) — без них теряется до половины мелких правок.
- Фильтруй по признакам поломки («не работает», «опять», «всё ещё», 403/404/500); дедуплицируй по тексту —
  возобновлённая сессия повторяет те же реплики и рождает ложные пары.
- Окно меряется репликами, а не сессиями: меньше двадцати — расширяй и скажи об этом прямо, а не выдавай
  четыре случая за закономерность.
- Сгруппировал по темам — обязательно посчитай механически, на скольких объектах правило соблюдено (например,
  общий стиль шапки на 32 из 50 экранов). Правило на двух третях объектов — совпадение; закрой разрыв и
  преврати правило в исполняемую проверку.
