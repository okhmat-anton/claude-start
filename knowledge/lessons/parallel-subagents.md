# Волна исполнителей-субагентов: лимиты и общие ресурсы

Контекст: десять долгих исследований запустили одновременно фоновыми субагентами на сильной модели,
часть из них запускала собственных помощников. Лимит сессии кончился дважды посреди работы, общий
поиск в сети — за первые часы; параллельные исполнители затирали друг другу временные файлы.

Урок:
- **Не больше 4 исполнителей одновременно**, следующий — когда освободилось место. В задании прямо:
  «своих помощников не запускай» — вложенные субагенты множат расход незаметно для главного агента.
- Уточняющие вопросы человеку задаёт главный агент до запуска и передаёт ответы в задании: фоновый
  исполнитель спросить не может, а угаданный ответ перечёркивает часы работы.
- **Поиск в сети (WebSearch) — один лимит на всю сессию** (порядка 200 запросов), его съедают первые
  исполнители. Запасной путь заложить в задание сразу: выдача поисковика в настоящем Chrome без окна
  через CDP и прямые адреса первоисточников через WebFetch. Поисковики через curl отдают мусор, 429 или капчу.
- Исполнителя прервал лимит — **продолжать его же** (SendMessage по id), а не запускать нового: собранное
  остаётся в его памяти и в рабочей папке. После волны прерываний — первыми тех, кто ближе к финишу,
  по двое: при новом лимите меньше недоделанного.
- Временные файлы в общей папке — с приставкой исполнителя; одинаковые имена служебных скриптов
  параллельные исполнители перезаписывают друг другу молча.
- Субагенту запрещено создавать файл отчёта `.md` — промежуточный текст писать в `.txt`, инструменты,
  которые принимают файл, расширение обычно не проверяют.
- Общие требования окружения (например, программа, превращающая страницы PDF в картинки для проверки)
  проверить **до** запуска волны: иначе каждый исполнитель пишет свой обход.
- Готовую работу главный агент проверяет сам по факту (статус, файлы, отправка), а не по отчёту исполнителя.
