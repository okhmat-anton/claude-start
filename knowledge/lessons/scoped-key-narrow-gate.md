# Ограниченный ключ проходит общую авторизацию, но не любой маршрут

Контекст: система выдаёт узкие ключи доступа (например, «ключ проекта» для внешнего
агента) — сервер принимает такой ключ наравне с личным токеном на уровне общей
функции авторизации, а дальше по каждому маршруту должен стоять СВОЙ отдельный
gate, ограничивающий, что именно ключ может делать. Гайд для агента при этом
перечисляет действия («после результата — оставь комментарий в разделе X»),
не проверяя, что gate на этот раздел вообще навешан для такого типа ключа.
Агент по гайду начинает действие и получает отказ уже на последнем шаге — там,
где переделка стоит дороже всего.

Урок:
- Ключ, прошедший общую авторизацию, не значит «есть доступ везде» — у него есть
  доступ только там, где для его типа явно описан gate прав. На остальных
  маршрутах он либо честно получает отказ, либо (если gate забыли навесить)
  тихо проваливается в доступ более широкого уровня — оба исхода одинаково
  не означают «этот раздел ему доступен по замыслу».
- Прежде чем выполнять шаг из чужого гайда/протокола ограниченным ключом,
  особенно ЗАПИСЬ в раздел, не являющийся тем, под который ключ выдан, — сделать
  один пробный вызов и прочитать причину отказа, а не описание в гайде.
- Гайд, который обещает действие ключом, — обещание документа, а не факт прав;
  когда права не совпадают с обещанием, это повод поправить документ (добавить
  условие или ссылку на нужную галочку доступа), а не искать способ обойти
  ограничение более широким токеном молча.
- Если для завершения шага действительно нужны более широкие права — это
  делает тот, у кого они есть (владелец или процесс с полным токеном) по прямой
  просьбе, а не автоматическая эскалация самим агентом.
