# Read-only эндпоинт под токеном для внешнего потребителя

Контекст: сервис отдаёт данные чужому дешборду по ссылке. Потребитель — машина: ссылку вставляют в поле «URL
источника», заголовок прописать некуда. Самая частая ошибка — «пусть пока отдаёт нули, потом настроим»: дешборд
рисует нули как факт, и никто не замечает, что мониторинга нет.

Урок:
- Токен в пути; за это он даёт только чтение и только неопасные данные (попадёт в логи прокси).
- Три состояния: токен не настроен → 503 с причиной; неверный → 404 (401/403 подтверждают, что эндпоинт есть);
  верный → 200. Никогда 200 с заглушкой.
- Форма JSON — контракт с тем, кого не выкатишь одновременно с собой: ключи не переименовывать, новые в конец,
  недоступная метрика — `null`, не `0` («нагрузки нет» и «неизвестно» — разные утверждения).
- Секреты сравнивай по байтам: `secrets.compare_digest` на строках падает 500 на первом не-ASCII токене. Тест —
  с намеренно не-ASCII значением, на ASCII баг не воспроизводится никогда.
- Есть маршрут-перехватчик (короткие ссылки, catch-all) — вешай эндпоинт под общий префикс API, не в корень.
- Печатая такие ссылки в вывод или отчёт (проверка после релиза), маскируй сегмент-токен пути
  (`sed -E 's#/[0-9a-f]{32,}#/***#g'`), а не только `?token=`: токен в пути утекает целиком.
