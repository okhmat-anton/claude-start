# PDF-отчёт — оформленный, а не распечатка текста

## 1. Где взять набор

Если у владельца есть планировщик с проектной картой (адрес сервера и ключ
проекта — в инструкции проектного агента), готовый набор и полный протокол
отдаёт он сам: `GET <сервер>/api/pdf-kit` → поле `protocol` (прочитать
целиком) и поле `install` (одна команда скачивает скрипт, стили, графики,
шрифты в `.pdf-kit/`). Работает с ключом проекта; своего кода писать не нужно,
`.pdf-kit/` и `pdf-reports/` — в `.gitignore`. Дальше — по протоколу из
набора, он главнее этого текста.

Планировщика нет — ниже архитектура, чтобы собрать такой же инструмент.

## 2. Что писать — структура по типу

Вёрстка меняет вид, а не смысл: сначала текст, и только из него — цифры.

- **Отчёт по ресёрчу / ответ на поставленный вопрос:**
  1) вопрос дословно;
  2) ответ в 3–5 строк — врезкой;
  3) как искали: источники, сколько, даты, что не открылось;
  4) находки по темам — у каждой цифра или цитата и ссылка;
  5) где источники расходятся — обе стороны с весом, сторону молча не выбирать;
  6) что это значит для проекта;
  7) шаги с исполнителем;
  8) ограничения выборки.
- **Документ инвестору:**
  1) проблема и для кого;
  2) решение и одна главная фишка;
  3) почему сейчас;
  4) рынок и конкуренты — с источником и датой;
  5) модель денег и экономика одной продажи;
  6) что уже доказано;
  7) вехи с датами;
  8) команда;
  9) три сценария и точка безубыточности;
  10) запрос: сколько, на что, какие вехи покупают эти деньги;
  11) риски.
- **Бизнес-план / КП / финмодель** — оффер или вывод первым экраном, одна фишка
  в заголовке (успешные продуктовые кампании держатся на одной, а не на списке
  характеристик), три сценария, точка безубыточности, конкуренты таблицей с
  «есть / нет / частично» и графиком цены.

## 3. Архитектура инструмента

1. **Markdown → HTML-скелет.** Построчный разбор: заголовки → разделы с
   номером, таблицы, списки. Inline-разметку (`**жирный**`, ссылки) разбирать
   **по всему пункту списка целиком**, а не по каждой физической строке:
   иначе жирный, перенесённый внутри пункта, останется звёздочками.
2. **Компоненты + графики из JSON.** Обложка на всю страницу, плитки главных
   цифр, врезки (вывод / риск / внимание), карточки тарифов, картинка к
   разделу, оффер с кнопками. График — `<figure data-chart='{JSON}'>`, один
   рендерер рисует SVG по ширине колонки: столбцы, полосы, линии, кольцо,
   составные полосы, этапы по датам (с вехами), карта «вероятность × влияние».
   Одна проверенная палитра на все типы. На тёмных блоках явно задать светлый
   цвет и жирному тексту — иначе он наследует тёмный цвет текста и пропадает.
   Подписи вех на графике этапов разводить по строкам, если они наезжают друг
   на друга. Полоса «от–до» рисуется от начала диапазона: итоговую сумму с
   разбросом рядом с одиночными значениями рисовать значением по верхней
   границе с подписью диапазона — иначе самая дорогая позиция выглядит
   самой короткой.
3. **Печать headless Chrome** (`--headless=new --print-to-pdf`). Готовность
   определять по содержимому файла (`%%EOF` в конце), а не по выходу процесса,
   и удалять старый PDF перед печатью. Иначе старый файл пройдёт проверку
   раньше, чем Chrome допечатает новый. Процессы Chrome гасить группой. Любой
   элемент шире колонки печати ужимает весь документ — у обложки без полей
   появится белая кромка.
4. **Раздача набора по API.** Если PDF собирают агенты на разных машинах —
   отдавать скрипт, стили и протокол с сервера (манифест + файлы по
   белому списку), а не просить доступ к репозиторию. Одна команда `install`
   качает всё по манифесту. Протокол — один файл: он же лежит в наборе и
   уходит по API.

## 4. Картинки

Обложка (2:3) и 2–3 картинки к разделам (16:9) в одной палитре. В промте —
предмет, свет и стиль; явный запрет цифр, букв и логотипов: данные живут в
тексте и графиках. Картинки платные — до генерации назови их число.

## 5. Проверка перед отправкой

Каждая страница PDF — в PNG (`pdftoppm`) и прочитана как картинка. Обрезанные
подписи, наложения, полупустые страницы и звёздочки вместо жирного видны
только на растре. Текст и цифры совпадают с источником. Регрессии набора
(разбор жирного, цвета на тёмных блоках, раскладка подписей) закрепить
проверкой, а не описывать в протоколе как «грабли».
